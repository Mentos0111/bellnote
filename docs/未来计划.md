## 1. 桌面小组件

### 要解决什么

- 现在看今天的安排要先点开 App：首页 → 全部日程。桌面没有任何入口。
- 真实场景：上课前扫一眼桌面，就知道下一节是什么、几点、还剩多久。

### 做成什么样（V1 范围）

- 两个尺寸：
  - **2×2「下一件事」**：标题 + 开始时间 + 倒计时（还有 12 分钟）。
  - **4×4「今天」**：今天剩余 4–6 条，左侧时间列，已结束的淡出。
- 只读：点空白处进 App；点某一条跳到那条的编辑页。
- 跟随 6 套配色 + 深浅色，不另造一套颜色。
- **V1 明确不做**：小组件里直接勾完成、滚动浏览、月视图、锁屏小组件。

### 技术路线

- `AppWidgetProvider` + `RemoteViews`。**不引 Glance / Compose**：项目是纯 View 体系，引 Compose 会把 APK 和构建复杂度抬一截，这点收益不值。
- 新增文件：`service/TodayWidget.kt`、`service/AgendaWidget.kt`、`res/xml/widget_*_info.xml`、`res/layout/widget_*`、`res/drawable/widget_*`。
- 数据直接读 `TodoStore`，不另建表。
- 刷新三路：
  1. App 内任何写操作后主动 `notifyAppWidgetUpdate`；
  2. 系统 `updatePeriodMillis` 30 分钟兜底；
  3. 待办开始 / 结束时精确刷一次——V1 用 WorkManager（15 分钟粒度），倒计时按「分钟」显示，精度够，也不必申请精确闹钟权限。
- 点击用 `PendingIntent.getActivity` + `FLAG_IMMUTABLE`，深链复用 `EditActivity` 已有的 extra。
- 配色：`RemoteViews` 里拿不到 `?attr`，得在代码里把当前配色解析成具体色值，再 `setTextColor` / `setInt(R.id.x, "setBackgroundColor", …)`。**这是最容易做成「只有浅色好看」的地方，要单独过一遍。**

### 预判的坑

- RemoteViews 只支持有限布局（LinearLayout / FrameLayout / TextView / ImageView / Button / ProgressBar…），自定义 View 一律不行。
- Android 12 起小组件自带圆角裁剪和内边距，内容要留 16dp 安全边。
- 桌面 launcher 会缓存旧布局，改版后要用户删掉重新添加，或杀一次 launcher。
- 进程被杀后小组件仍要能显示——不能依赖 Activity 里的内存缓存。

### 拆几步

1. 静态版：4×4 只显示「今天 N 条 + 前 3 条标题」，接上 provider 和 info xml，真机能加到桌面。
2. 接数据：读 TodoStore，按开始时间过滤今天；补空态文案。
3. 配色：6 套 × 深浅逐个截图核对。
4. 2×2 倒计时版。
5. 刷新链：写操作通知 + 30 分钟兜底 + 开始时刻刷新。
6. 点击跳转 + 单条深链。

### 怎么算过关

- 6 套配色 × 深浅两态，桌面截图里没有看不清的字。
- 新增 / 删除 / 改时间一条待办，回到桌面 5 秒内已变。
- 跨过开始点变「进行中」，跨过结束点该条淡出或消失。
- 加 / 删小组件不崩；App 进程被杀后仍正常显示。

## 2. 导入课程表

### 要解决什么

- 建一学期的课要手动敲几十条，每条还得选「每周」——但「每周」写不进单双周，也写不进「只上 8 周」。
- 目标：一次导入一张课表，之后自动按周次落成日历事件。

### 做成什么样（V1 范围）

- 输入：相册里的课表截图 / 从别的 App 分享图片进来 / 现有「拍照识别」。
- 识别：复用现有 OCR 与视觉链路（`ai/OfflineOcr`、`ai/VisionExtractor`），但**换一份课表专用提示词**——要模型按「星期 × 节次」的网格返回课程，不是现在的「一条待办」。
- 中间确认页：识别完先给一张可改的表（课程名 / 星期 / 第几节 / 周次范围 / 单双周 / 地点），能删行改行，确认后才写。
- 写入：生成**重复日历事件**，不是几十条独立事件。
- **V1 明确不做**：自动登录教务系统抓课表、xlsx / csv 批量导入、和学校 App 同步、课表周视图（先只为导入服务，视图以后再说）。

### 数据模型要先扩

现有 `RepeatRule` 只有 5 档 `FREQ=…`，装不下课程表。要先做三件事：

1. `RepeatRule` 扩成规则对象：`FREQ` + `BYDAY` + `INTERVAL` + `UNTIL` / `COUNT`。
2. 课程单独一张表（同一 DB 加表）：名称、地点、星期、开始 / 结束时间、起止周、单双周、颜色。
3. 删除 / 重导入要能「按课程整体替换」，不能留下上次导入的僵尸事件——接到现有的 `DeleteWindow` / `TitleKey` 对账逻辑上。

### 拆几步

1. 模型层：RepeatRule → 规则对象，补单测（每周 / 单双周 / 指定周次 / 有结束日期）。
2. 确认页骨架：本地造 3 门课渲染，先看版式。
3. 识别：课表专用 prompt + 网格结果解析，先用现成截图离线跑通。
4. 写入：课程 → 重复事件，挂对账。
5. 重导入替换逻辑。
6. 一张真实课表跑一遍，人工核对一整周。

### 怎么算过关

- 一张真实课表截图 → 3 分钟内改完并写入，人工核对「星期 / 节次 / 周次」无错。
- 手机上日历里看到的是「每周重复到第 N 周」，不是几十条散事件。
- 同一张课表导入两次，不产生重复事件。
- 只支持「连续周次」和「单双周」两种；遇到跳周要明确提示不支持，不能静默写错。

## 3. 版本检查与更新日志

### 要解决什么

- 现在装了之后就是「装到哪一版算哪一版」：App 自己不知道有没有新版，用户也不知道。
- 想让人知道自己落后了几版、这版改了什么，得靠人把链接一个个发出去——发一次还行，发十次就没戏了。
- 目标：打开 App 就知道「有没有新版 / 新版改了什么 / 去哪下」，不用等人通知。

### 做成什么样（V1 范围）

- **设置 → 诊断与帮助 → 新增一行「检查更新」**，右侧显示当前版本，例如「3.21.5 · 已是最新」或「3.21.5 · 有新版本 3.22.0」。点进去是更新详情页。
- 更新详情页：新版版本号 + 发布日期 + 这一版改了什么（读 `CHANGELOG.md` 对应小节，纯文本排版）+ 一个「去下载」按钮（跳系统浏览器打开固定的国内直链）。
- **有新版时**，首页顶部出现一条可关闭的细提示条（不是弹窗，不抢焦点）：`发现新版本 3.22.0 · 查看`。
- 自动检查：冷启动后 10 秒查一次；同一天最多查一次（24 小时内不重复）；只在 Wi-Fi/移动网都查，不做网络类型判断。
- **V1 明确不做**：应用内直接下载并安装（要 `REQUEST_INSTALL_PACKAGES`、FileProvider、各厂商安装校验弹窗，坑多且容易被当恶意软件）、增量更新、强制更新、版本回滚、灰度发布。

### 技术路线

- **发布侧**：CI 在发版时多产一个 `version.json`（字段：`versionName` / `versionCode` / `publishedAt` / `downloadUrl` / `sha256` / `notes`），跟 APK 一起挂到 Gitee 的 `latest` 发行版里，地址固定：
  `https://gitee.com/Mentos0111/bellnote/releases/download/latest/version.json`
  ——和「永远指向最新版」的 APK 链接同一套机制（`scripts/gitee_sync.py --latest`），现在已经跑通，加一个附件即可。
- **客户端**：新增 `net/UpdateChecker.kt`。用 `HttpURLConnection` GET 上面那个固定 URL（只读公开地址，不带任何 Key），解析 JSON，比较 `versionCode`（现有规则：`major*10000 + minor*100 + patch`）。
- 请求头只带 `User-Agent: Bellnote/<versionName>`；**不上报任何设备信息、不生成设备 ID**，服务端也没有日志分析需求。
- 失败一律静默（超时 8 秒、任何异常都当「没查到」），绝不因为检查更新影响启动或弹错误。
- 结果缓存进 `Prefs`：`lastUpdateCheckAt`（时间戳）、`latestKnownVersionCode`、`latestNotes`。设置页直接读缓存渲染，不用等网络。
- 详情页的「去下载」用 `Intent.ACTION_VIEW` 打开 `downloadUrl`（http/https 都走系统浏览器，App 内不引 WebView）。
- 提示条只在「缓存里已知有新版」时出现，且可关闭；关闭后同版本不再提示（记 `dismissedVersionCode`）。

### 预判的坑

- 国内网络：GitHub 拉不到，所以**下载地址与 version.json 都只认 Gitee**，不要在客户端里写死 GitHub 链接。
- Gitee 附件下载会给 APK 加 `.apk.zip` 后缀（已知），所以「去下载」只管打开浏览器，安装交给用户；文案里要带一句「若是 .apk.zip，删掉 .zip 再装」。
- `version.json` 里的 `notes` 是中文多行，客户端解析要按 UTF-8，别用默认编码。
- 别把「检查更新」做成启动阻塞项：一律后台线程 + 失败静默。
- 若将来 Gitee 挂了，`downloadUrl` 由 JSON 决定，改 JSON 就能换渠道，不用发版——这是把地址放进 JSON 而不是写死代码的原因。

### 拆几步

1. 发布侧：`version.json` 生成脚本 + 挂进 `latest` 发行版，先用 curl 手动验一遍内容。
2. 客户端 `UpdateChecker`：拉 JSON、比较版本、写 `Prefs` 缓存；配 4 条单测（有新版 / 无新版 / 网络失败 / 旧缓存）。
3. 设置页新增一行「检查更新」（分组、文案先问本人定）。
4. 更新详情页：版本号 + 日期 + 说明 + 去下载。
5. 首页提示条（可关闭）+ `dismissedVersionCode`。
6. 真机验证：故意把本地 `versionCode` 调低，看它能不能发现「新版」。

### 怎么算过关

- 装 3.21.5、服务端放 3.22.0：设置页 10 秒内显示「有新版本 3.22.0」，说明文字与 CHANGELOG 一致。
- 点「去下载」能用系统浏览器打开国内直链；断网时静默、不崩、不弹错误。
- 同一天反复冷启动不重复请求（抓包或看 `lastUpdateCheckAt`）。
- 关掉提示条后同版本不再冒出来。
- 检查更新不增加启动耗时（冷启动到首页可交互的时间差 < 50 ms）。
